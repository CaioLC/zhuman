# Product roadmap

**The only document that discusses what is not built.** Gaps, limitations, sequencing, deferred ideas, and arguments about future work belong here and nowhere else. Present-tense product rules live in [`design.md`](design.md) and [`ui_design.md`](ui_design.md); implemented architecture lives in [`../src/README.md`](../src/README.md), [`../src/ui/README.md`](../src/ui/README.md), and [`../src/ui_client/README.md`](../src/ui_client/README.md).

Work is split below by architectural responsibility and tied back together by the delivery order. `src/ui/` remains a generic, extractable immediate-mode engine; `src/ui_client/` binds that engine to SDL; `src/pages/templates/` owns game-specific reusable compositions; `src/pages/` owns screens and applies user intent to the simulation; simulation modules own authoritative rules and atomic state changes.

## 0. Contract for using the prototypes

### Source precedence

When two references disagree, use this order:

1. `prototypes/menu.html`, `prototypes/title.html`, `prototypes/market.html` and `prototypes/trade.html` (the most recent decisions; they win over anything older that contradicts them), then `prototypes/act-i.html` and `prototypes/act-ii.html`, as the rendered-product and interaction truth, including their current embedded scripts. The act pages frame `trade.html` (behind `TRADE →`) and `market.html` (Act II's MARKET tab) rather than carrying copies.
2. `prototypes/prototype.css` for exact visual tokens, density, state styling, breakpoints, clipping, and transition timing.
3. `prototypes/UNIFIED_UI_SPEC.md` for cross-act component identity, vocabulary, and normalization decisions.
4. `src/README.md` ("The research board") and `assets/roster/technologies.zon` for the Act II board topology, coordinates, technology roster and board invariants; the migration rules are `src/sim/data/migration.zig`'s.
5. Screenshots in `prototypes/` as visual regression fixtures. Screenshots with older merchant wording or the obsolete direct-barter Act II exchange do not override current HTML.
6. `docs/design.md` and `docs/ui_design.md` for game rules outside the rendered prototype. An unresolved economic rule remains a blocker or fixture-backed interface; UI code must not silently invent it.

The prototypes have no visible `blocked` recipe state, one normalized merchant modal, query-and-sort BUILD in both acts, collapsible milestone cards, and per-view Holdings collapse. Dead CSS or stale screenshot text is not a feature request. HTML is authoritative for rendered behavior; the explicit cross-act economic and topology invariants below override fixture-data drift. In particular, the unified `1:1` rule makes the Act I `12m` versus Act II `8 biomass` Garden bed mismatch a bug: normalize the shared recipe to `8` rather than preserving two prices.

### Native translation rules

The implementation is not a browser port and must not grow a CSS or DOM interpreter.

- CSS selectors become explicit Zig template state and style fragments.
- CSS grid layouts become the smallest required engine sizing primitive plus ordinary row/column composition. A general web-grid engine is out of scope.
- Media queries become frame-local `ViewMetrics` and explicit compact/narrow template branches.
- ARIA becomes keyboard behavior, visible focus, semantic metadata, and an accessibility bridge where the platform supports one.
- URL hashes/query parameters are prototype review controls, not player-facing desktop requirements. Equivalent deterministic states belong in a development fixture/deep-link harness; normal tab, query, sort, disclosure, camera, and collapse state persists in keyed UI/session state. No equivalents of `window.prototype*`, DOM CustomEvents, hash routing, or query-parameter state belong in game code.
- Native HTML controls (`dialog`, `search`, `select`, `range`) become reusable SDL controls with equivalent pointer, keyboard, focus, disabled, and dismissal behavior.
- Prototype JavaScript that mutates balances is illustrative wiring. Production UI calls authoritative simulation operations and never completes half of a trade, build, research payment, or act transition locally.

### Non-negotiable product invariants

- Act I has Vigor, Food, and generic Materials; Act II has Vigor, Population, Coin, Food, Water, Fuel, Metal, Minerals, and Biomass.
- At the Act I curtain, Food carries unchanged and unspent Materials converts to Biomass at exactly `1:1`. Built goods remain built. Same-named Act I material costs and Act II biomass costs remain numerically equal.
- Energy is a flow/rate in the runline, never a stockline balance.
- Act I has ACTIONS and BUILD. Act II has ACTIONS, BUILD, RESEARCH (the board, formerly STRUCTURE), and MARKET (the neighbours view). ACTIONS lists the held generator verbs after the labor verbs; Act II's lists the union of the Act I and Act II generators held.
- ACTIONS is one pane in both acts: it searches, sorts and hides its tiles. Act I's tiles are at the regular density, Act II's compact.
- BUILD uses one data-generated six-column recipe catalog in both acts. Act I lists the recipes whose gates pass, so a manufactured recipe appears once the crude good before it is owned, and dims the ones short; Act II lists its complete shelf, research-gated rows dimmed. Newly eligible recipes appear with an event-log announcement.
- Recipe states visible to the player are `ready`, `reach`, `owned`, and `building`; milestone states are `locked`, `unfunded`, `ready`, and `done` (`built`/`standing` copy is act-specific).
- Shelter and Exchange share one milestone component. Passerby, Merchant, and Exchange share one market-strip/trade-dialog skeleton with identity-specific wording.
- Holdings collapse is remembered separately for ACTIONS and BUILD. Entering a focus view (RESEARCH, MARKET) forces collapse each time without overwriting those memories.
- ACTIONS and BUILD retain the four-line event log and the merchant/activity strips. The focus views hide them.
- **Parity rule.** Zig reproduces the prototypes visually and functionally; only content (goods, prices, names) may differ. A screen whose backend does not exist yet is built against a stub or fixture, never omitted.
- The Act II board contains one noninteractive ring-0 foundation plus exactly 60 technology tiles in rings 1–4. It does not reserve Act III rings.

## 1. Delivery order

1. **Act I transition:** the versioned Act I → II migration (`ACT1-18`).
2. **Act II backend:** population, typed ledgers, the catalog graph, quotes, snapshots, autonomous deciders, demand and exchange rules, transaction evidence (`ACT2-*`, `CAT-03`).
3. **Hardening:** domain and lifecycle tests, keyboard-only journeys, performance and leak checks, provenance (`QA-*`).

Live Act II UI requires typed ledgers and catalog snapshots (`ACT2-01..07`); a fixture-backed screen is not product completion. The gaps in section 2 block nothing in this order and are picked up where a consumer needs them.

## 2. Engine and host gaps — `src/ui/`, `src/ui_client/`, the shell

- [ ] **UIE-11 — Give an in-tree popup a top layer.** *Deferred: no screen has an in-tree popup (nothing uses `select`); pick this up only when one is designed.* The paint walk is pre-order and the hit test follows paint order, so an anchored child such as the select's popup is painted under, and loses pointer hits to, every node that comes later in the tree: a `select` opened above later siblings sits beneath them (no shipped screen uses `select` today; the debug page does). The only overlays that float today are separate roots (tooltip, modal). Either a deferred-paint flag that the stamp and render walks honour after the rest of the tree, which keeps hit order consistent with paint order, or the popup as its own root handed up through the page's root list. Until then a select's options are reliable only where nothing follows them in the tree.
- [ ] **SHELL-05 — Settings that act and persist.** Difficulty, music, effects and contrast on `Resources.settings` are shown and held but drive nothing (window size, fullscreen and UI scale do act), and no setting survives a launch: a save holds a run, not the settings.

## 3. Act I — act transition

- [ ] **ACT1-18 — Implement a versioned Act I → II migration.** Carry Food unchanged; convert only unspent generic Materials to Biomass `1:1`; preserve goods/counts/effects; remove generic Materials from active Act II accounting; seed Foraging/Woodcutting researched and the remaining ring-1 states per the board spec; initialize population/capacity/market state exactly once. Unit-test idempotence and save-version boundaries. In place: `migration.migrate_to_act_two`, which converts Materials, opens the other Act II stocks empty, seeds the board with `Research.entry` and stamps `Migrated`, each rule tested. `cross_curtain` runs it on the player on entering Act II, and population/capacity/market initialization is the `population_seeded` seam until ACT2-01. A save carries a `version` (`sim/data/save.zig`) and refuses another; `Migrated.version` is the stamp on the agent.

## 4. Act II authoritative backend and shell

Prototype catalogs are deterministic UX fixtures, not permission to hardcode economic outcomes in templates. Stable interfaces may be implemented against fixtures first; live completion requires the following domain work.

### Population, ownership, and catalogs

- [ ] **ACT2-01 — Add population lifecycle and stable identities.** Shelter capacity, sustained surplus, and starvation drive arrivals/departures; every person has stable ID/display label, Vigor, current work, and specialization state. The player remains one agent. Expose current population/capacity as a frame-consistent read. Reuse the capacity the shelter record already carries (`capacity`, summed by `capital.capacity`—today read only by a test) rather than introducing a second ceiling. In place: `Sim.population` is a stand-in count, `Sim.neighbours` (`sim/rules/neighbours.zig`) a deterministic stand-in book of 24 people the MARKET view reads and trades with, and the reserve a stub table in `sim/systems/neighbours.zig`.
- [ ] **ACT2-02 — Add per-agent typed ledgers.** Represent Food, Water, Fuel, Metal, Minerals, Biomass, Coin, and goods with stable IDs and ownership transfer APIs. Settlement totals are derived snapshots, not a shared mutable inventory. Generic Materials cannot be earned/spent after migration. Extend `market.Ware` and `Bundle` rather than adding a second transfer grammar; Act I's bundles, quotes, and refusal ladder are the shape to grow. In place: stock components for Food, Materials, Biomass, Water, Fuel, Metal and Minerals behind `ledger.Stock`, the Act II ones opened at the curtain; Coin has none until ACT2-09, and the merchant's lots are fixture records in `sim/systems/merchant.zig` until it has a ledger.
- [ ] **ACT2-03 — Build an authored catalog graph and complete category data.** Every action/material/good/technology has stable identity, act, sector(s), production stage, category/type, recipe, costs, duration, effects, inputs/outputs, and optional research linkage. Inputs distinguish consumed, retained/tooling, upkeep, and produced; consumed intermediates reuse the count semantics already exercised by Act I. Several inputs may converge on one output, and seam goods may name two sectors. The Act I roster is sixteen second-order goods that make food/comfort while nothing makes them; the Act II records add intermediates such as cut stone and a forge, but a production stage is not a field. `src/sim/tags.zig` stops at `Food`/`Comfort`/`Tool`/`WoodCutting` and nothing reads those tags, so complete the set as part of this catalog—the RESEARCH specialization/category model is its first load-bearing consumer. The authored roster (`src/sim/data/roster.zig`, `assets/roster/`) already carries ids, acts, sectors, research gates and amounts keyed by resource; the category and stage fields belong on its records rather than a second table. Two Act II shapes wait on this design: the intermediates (cut stone, the brick press, glass panes, the saw pit, the lime kiln) build one unit where the prototype built a lot, and the goods whose copy names a yield (the ropewalk, the fishing net, the irrigation pump, the apiary, the pump house) open no generator verb yet. The board's cost balance is an intent, not data: outer rings cost more, and completing every wedge is meant to be infeasible, so a settlement specializes in roughly 40 to 50 percent of the board.
- [ ] **CAT-03 — Move the remaining authored tables to files.** The passerby's wares and sell schedule, `Config`, and the starting verbs `sim/systems/run.zig` names (`starting_verbs`) become files the same loader handles; the Act II fixture tables (`pages/act_two/fixtures.zig`) become ZON fixtures the harness loads.
- [ ] **ACT2-04 — Preserve economic openness.** Production structure is displayed and costed, not a hard dependency lock. Cross-specialization production remains legal at a penalty. Keep `prereq_of` only where a modifier truly requires a target verb. A merchant must remain an alternative, not a key that grants permission to build. This is the Ricardian point of the act: trade should pay even when a person could make everything themselves; forcing trade because an input is impossible would foreclose the comparative-advantage demonstration.
- [ ] **ACT2-05 — Add production/action quotes per agent.** One calculation returns typed deficits, Vigor/energy/time price, expected output distribution, Busy/standing reason, specialization multiplier, and eligibility. ACTIONS, BUILD, RESEARCH effects, AI decisions, and resolution consume the same quote. Test quote/resolution agreement.
- [ ] **ACT2-06 — Expose a frame-consistent market/agent snapshot.** Selected agent, observable holdings/demands, counterparties, offers, revisions, population, catalogs, research state, and balances must come from one coherent revision while autonomous decisions run.
- [ ] **ACT2-07 — Generalize decide → act.** The split currently exists only in shape: the player is the sole decider and there is no AI decider. AI agents must enumerate and invoke the same labor, consumption, action, build, offer, trade, and specialization operations as the player's UI. UI visibility must never be required for simulation progress.
- [ ] **ACT2-08 — Resolve open demand/specialization/exchange-ratio rules before live wiring.** Specify subjective ordinal demands, quantity-sensitive marginal ranks, observability, comparative-advantage/learning rule, bilateral negotiation mechanism, and autonomous ranking policy in `docs/design.md`; keep this roadmap entry until implemented. Specialization state and the operation that changes it are simulation rules—the UI must not assign a profession merely because a player clicks a colored board wedge. Bilateral offers carry counterparty, give/receive typed bundles and quantities, expiry, revision, and status; counteroffers preserve lineage; acceptance settles atomically across both private ledgers and returns both agents' post-trade holdings. The chosen rule must say whether acceptance follows posted prices, bargaining, or a market mechanism. Do not substitute a shared utility score or hardcode every agent to a UI slider threshold. The open questions as the design document posed them: how demands form (subjective ordinal preferences over food and materials, needs and thresholds, and how per-agent deciders degrade to aggregate demand at scale); how an exchange ratio forms (posted price, bilateral bargaining or double auction); what specialization is (skills, comparative advantage from differing yields and vigor, or learning-by-doing); and how an autonomous decider ranks the catalog under scarcity. Per-agent inventories are ACT2-02's.
- [ ] **ACT2-09 — Record transaction evidence and model money emergence.** Completed trades feed bounded history keyed by good pair with quantity, time, and direction. Displayed ranges derive from evidence, state when evidence is absent, and never become an unexplained global price table. Act I's fixed merchant exchanges use the same transaction-record shape while remaining explicitly quoted trades, not fake market discovery. If a medium of exchange emerges, agents need acceptance of and demand for that good, and settlement must distinguish direct from mediated exchange. The HUD exposes the medium and balance only after the simulation recognizes one; a day/act threshold cannot create a coin counter.

### Exchange and Act III identity transition

- [ ] **ACT2-20 — Preserve person-level economics through later scale transitions.** Individual decisions remain authoritative throughout the Act II band. If a later aggregate model replaces any of them, it must preserve person-level ownership, subjective ordinal demand, and transaction history as observable economic facts; aggregate totals must never silently become shared inventory.

## 5. Verification and acceptance

### Automated tests

- [ ] **QA-05 — Add Act II domain tests.** Cover typed transfer atomicity/ownership, population boundaries, quote-resolution equality, research adjacency/payment, technology↔recipe links, Merchant settlement, Exchange `500/501` boundary, Exchange payment/completion, and one-time Act III transition.

### Deterministic UI fixture harness

- [ ] **QA-20 — Template-level state and lifecycle tests.** Hide and show through a state pointer (BUILD's query and sort survive the ACTIONS tab), reorder by domain key, a focused control disappearing, independent ACTIONS and BUILD state, modal opener restoration and initial focus, scroll preservation. Needs the fixture harness (`HA_FIXTURE`) and the replay driver (`ui_client/replay.zig`) plus an SDL-free text measurer: a template with a text leaf measures through the platform font, which is why only `control.zig` has lifecycle tests without a window today.

### Interaction journeys

- [ ] **QA-14 — Keyboard-only Act I journey.** Navigate tabs, change eating rate, start/cancel build, inspect/raise Shelter, open/switch/select/complete/close trade, and return focus correctly without a pointer. The interaction spine is automated SDL-free in `src/ui_client/journey.zig` (tab across the shell's roving nav + slider + trade action, Enter to activate, arrow to drive the eating-rate range owner, Escape to dismiss a trapped dialog, focus returns correctly); the live-page journey over the rendered screen awaits the SDL-free text measurer QA-20 also needs.
- [ ] **QA-15 — Keyboard-only Act II journey.** Search/sort actions and recipes, trade, open milestone details, enter RESEARCH, change filters/search/zoom, navigate/select/research a tile, clear selection, and leave with view state preserved. The catalog-controls spine is automated SDL-free in `src/ui_client/journey.zig` (the `/` search shortcut, Tab across search → sort → the roving view nav, roving arrow switches ACTIONS/BUILD, Shift+Tab reverses, disabled controls are skipped); the live-page journey over the rendered screen awaits the same SDL-free text measurer.

### Performance and resource acceptance

- [ ] **QA-17 — Profile representative worst cases.** At minimum: 20 actions, 50 recipes, open dialog, and all 61 board cells with rails/markers at 250%. Maintain the application's frame target on the reference machine without per-frame SVG loads or unbounded arena/pool growth. The five-pass `FrameProfiler` is the instrument; a development smoke capture on the Act I screen is not this evidence.
- [ ] **QA-18 — Run leak/lifecycle checks.** Repeatedly switch tabs, filter catalogs, open/close overlays, resize, and enter/leave RESEARCH; verify text/SVG/geometry textures and owned buffers evict, pointer capture/focus clears, and stale slots do not remain hittable.
- [ ] **QA-19 — Verify copy/data provenance.** Every displayed balance, requirement, deficit, duration, progress, stock count, effect, and readiness comes from one authoritative snapshot/catalog/quote. Search the implementation for duplicated prototype fixture numbers outside fixture/catalog data.

## 6. Explicit non-goals and deferred work

These remain in this file because it is the only future-work document, but they do not block Act I/II prototype parity unless a measured dependency proves otherwise. Act III's economy is deliberately unspecified beyond the sketch in `design.md`: firms, deeper division of labor, and a global source of capital goods the city buys from. That content cannot be designed honestly before Act II's demand/negotiation model in ACT2-08 exists; the Act III identity the raised Exchange opens does not pretend otherwise.

- [ ] **DEFER-02 — Capital durability/maintenance.** Goods are currently permanent once built; nothing wears. Add authoritative slow decay, condition, and upkeep before Holdings or a board tile displays a meter. Do not ship decorative wear UI.
- [ ] **DEFER-03 — Audio/music.** Add ambient music only after core UI/simulation lifecycle provides volume/configuration ownership.
- [ ] **DEFER-04 — Act III board thirds.** A later site may split one hex into three rhombi meeting at its center. This should cost the engine no new tiling concept—the same tile geometry, offset placement, and host-supplied hit predicate can compose it—so preserve APIs that allow adoption without a rewrite, but do not render or reserve thirds in Act II.
- [ ] **DEFER-05 — SparseSet scale policy.** `src/ecs/world.zig`'s `SparseSet(T)` holds three `[MAX_ENTITIES]` arrays (`dense_ids`, `dense_values`, and `sparse`) per component type, on the heap since `World.init(allocator)`, so memory cost is `num_types × MAX_ENTITIES`, not occupancy. Entity IDs are never recycled, making `MAX_ENTITIES` a lifetime-spawn cap rather than a live-population cap. This becomes material when the capital roster reaches hundreds or the ID ceiling must grow for population—not merely when there are hundreds of component types. It is why `comp.Quotes` carries each verb's standing and not its terms, which stay the read `actions.verbOf`; sizing to occupancy would let them in. Size dense arrays to occupancy; use a hashmap-backed sparse index for rarely carried types while hot types such as `Vigor` and `InventoryFood` retain flat indexing. Choose the per-type policy where `Storages(ns)` constructs each storage. Keep the change contained to the engine package, `src/ecs/world.zig` plus `src/ecs/query.zig`, whose `Query` driver must stop reading `.dense_ids`, `.dense_values`, and `.len` directly and use storage methods.
- [ ] **DEFER-06 — Additional sizing combinators.** Add `range`/`max_of`, `stretch`/`align-content`, and—only if measured compositions require it—a `strictness: f32` violation pass that distributes slack/overflow among siblings. Do not pre-build web layout breadth while `grow` plus per-axis min/max expresses the concrete responsive layouts. The one place a combinator is missing today: BODY does not stretch to HOLDINGS' height when the two sit side by side (`stretch`).
- [ ] **DEFER-07 — O(interactive) stamping.** Profile before attempting. The event stage is already O(interactive) because `mark` iterates live slots without a tree walk; `stamp_rects` is only one inexpensive O(all) pass among sizing, percentage resolution, placement, stamping, and drawing. Z-ordered hit testing does not retire it: the paint-order list must still be produced by this walk because query order is not paint order. QA-17 is the gate; the development smoke capture measured stamping at well under 1% of the five passes.
- [ ] **DEFER-08 — ZLS query tuple ergonomics.** `q.iter().next()` returns a `@Tuple`-constructed tuple that ZLS does not evaluate, so multi-fetch destructuring currently needs explicit annotations. Declaring `Query` parameters as concrete `[]const type` instead of `anytype` was measured and changes nothing; the limit is `@Tuple`. Complete type visibility only if ZLS's comptime interpreter gains that support.
- [ ] **DEFER-09 — Parameterized distribution curves.** If playtesting needs the mini-curve to encode an action's actual p10–p90 parameters rather than only its distribution family, generate it through the geometry feature and replace the five static SVGs in `assets/svg/`. Treat that as a reviewed extension to the finalized prototype, not a board prerequisite; the static assets stay until every live consumer (the action tiles) has migrated.
- [ ] **DEFER-10 — Change detection on components.** Bevy's `Changed<T>` is not built: the derived writers (`condition`, `outlook`, `quotes`) recompute every agent every tick. The trigger is a measured cost, not a population size.
- [ ] **DEFER-11 — One name for the markets.** `sim/rules/market.zig` (the passerby and the merchant) and `sim/rules/neighbours.zig` (the neighbour book) are both markets; the rename waits for ACT2-01, when the neighbours stop being a stub.
- [ ] **DEFER-12 — The UI script.** Screens written in a script the host evaluates instead of Zig composition, one of the UI engine's two long-range goals; the draft specification is [`feat-script-lang.md`](feat-script-lang.md).
- [ ] **DEFER-13 — Board chords.** Selecting a good lights every technology upstream of it on the research board, so the density of chords across wedges shows the division of labour. The board draws no chords.
- [ ] **DEFER-14 — Build multiples from the BUILD row.** A build yields one unit of the good, and a second unit is stock: it carries no second effect and is there to sell or hand on. The BUILD row takes a quantity, so the player orders several units in one go instead of repeating the build. The simulation already counts units per good (`comp.Goods`, `capital.finish`), so this is a UI affordance over the existing count, not a new rule.

## Definition of done

Act I/II implementation is complete only when no non-deferred item above remains and each of these is evidenced:

1. The production app reproduces the prototype shell, visual states, responsive layouts, and interaction state machines without HTML/DOM runtime code.
2. Every shared instrument is one reusable Zig component with act-specific data/vocabulary, not parallel copies.
3. All changing values and atomic operations are backed by authoritative simulation/catalog/quote state; fixtures exist only in the development harness.
4. Pointer, keyboard, focus, modal capture, scrolling, slider, catalog, and board-camera interactions pass automated journeys and visual review.
5. Act I transitions safely into Act II with the exact resource/research migration invariants; Act II can raise Exchange and switch to Act III identity exactly once.
6. `zig build`, `zig build test`, `zig build test-ui`, `zig build test-sim`, each engine package's own `zig build test` and `sh tools/boundary_check.sh` are green; required screenshot matrices and leak/performance checks are recorded; no escaped code `TODO` remains.
